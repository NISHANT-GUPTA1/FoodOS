# FoodOS — Team Split v2 (Agri Batch Blueprint)

**4 people · 36 hours · one repo · one objective function · zero merge conflicts**

Supersedes `FoodOS-Team-Split.md`. That document split the *kitchen* product. This one
splits the **perishable agricultural supply chain** product described in the Master
Execution Blueprint: batch profiles, RUL in hours, four ingestion layers, four specialist
agents, four screens.

---

## 0. The three rulings that make this a 36-hour job instead of a rewrite

Read these before you read your own section. Every task below depends on them.

### Ruling 1 — the agri surface is **additive**. Nothing existing is deleted.

The repo already contains a working engine: one objective function, a Q10 decay model, a
rescue waterfall, an AGMARKNET loader, four LLM agents with a numeric guard, seven
screens and a frozen API contract. All of it stays and keeps passing its tests.

The blueprint's batch product is built as a **new subject type on the same engine**:

| Blueprint asks for | Already exists as | Who extends it |
| --- | --- | --- |
| `V(a)` objective, single | `engine/optimiser.py::score()` | B — extend, never fork |
| Arrhenius / Q10 decay | `models/rsl.py` + `ingest/shelf_life.py` | A |
| RUL in hours | `engine/waterfall.py` already converts days ↔ hours | A |
| Rescue Agent diversion channels | `engine/rescue.py` + `waterfall.py` tiers | B (engine) / A (agent) |
| AGMARKNET / e-NAM prices | `ingest/agmarknet.py` (file connector) | D |
| Agents that never emit a number | `agents/base.py`, `guard.py`, `verifier.py` | A |
| Recommendation card | frozen shape in `contracts/api-contract.md` | C reuses it |

**If your task tempts you to write a second decay model, a second objective function, or a
second recommendation shape — stop and message the owner instead.** The platform claim in
the pitch ("one engine, many nodes") is false the moment there are two of anything.

### Ruling 2 — the demo is the **farm-gate batch story**. The kitchen screens become the platform proof.

Screens 1–4 of the blueprint (Command Center, Create Batch, Batch Intelligence, What-If)
are the pitch. The existing seven kitchen screens move behind one nav group and are shown
for ~20 seconds as "the same engine, a different node". Nobody rebuilds them.

### Ruling 3 — nothing opens a socket during the demo.

`docs/FoodOS-Blueprint-Reconciliation.md` already ruled out IoT hardware and live
telemetry, and the blueprint agrees (hardware is on its own out-of-scope list). Weather,
route and mandi data are **snapshot-first connectors**: they read a cached file, and only
attempt a network call when explicitly asked. The aeroplane-mode rehearsal at H34 must
pass. A connector that only works online is a connector that will fail on stage.

### The AI/ML rule

> **Person A is the only person who trains, calls, prompts, or fine-tunes a model.**

That covers all four of: the loss/RUL predictors, the vision pipeline, the LLM agents, and
the orchestrator. B, C and D consume A's functions and endpoints and never import a model
library. If B needs a number A has not shipped yet, B returns a deterministic placeholder
behind the same function signature and swaps it when A lands — **nobody blocks on A.**

To make that load carryable, everything AI-adjacent-but-not-AI was moved off A:
the commodity constants, the weather/route/market connectors, the questionnaire content
tree, the deck and the demo script are all D's. A writes models and prompts. Nothing else.

```
main                      <- always runnable, never broken
├── feat/a-intelligence   <- A: data, models, cv, agents
├── feat/b-batch-engine   <- B: schema, engine, api, ingest
├── feat/c-batch-ui       <- C: frontend
└── feat/d-telemetry      <- D: external, content, docs
```

Branch off `merge/b-integrated` at H2, after B's package move lands. Push every 60 minutes.
Merge into `main` at every sync point, in the order **A → B → D → C**. No PRs, no review —
straight merges. Commit prefix `[A]` / `[B]` / `[C]` / `[D]`.

`.env` is never committed. Photos and snapshots: `backend/data/external/*.json` **is**
committed (the offline demo depends on it); `backend/data/photos/` is not.

## 10. Out of scope — do not build these, no matter how much time is left

IoT sensor hardware · live GPS fleet tracking · item-level scanning · LSTM thermal
prediction · payment gateway integration · Beckn/ONDC as the primary surface · live
logistics routing beyond a distance/duration lookup · any commodity beyond tomato ·
multi-tenant accounts · training any model from scratch that is not the loss/RUL model.

Every one of these is already ruled out in `docs/FoodOS-Blueprint-Reconciliation.md` or on
the blueprint's own out-of-scope list. They do not come back at hour 28.

## 11. The five rules that decide whether you finish

1. **Nobody edits another person's folder.** File a request; the owner fixes it.
2. **Only A touches a model.** Everyone else consumes A's signatures and degrades gracefully.
3. **Everything rebuilds from `python -m foodos.ingest.seed`.** A demo that depends on a
   hand-edited database will not survive a laptop restart.
4. **One `score()`.** Three action spaces, four nodes, one objective function.
5. **After H30, a bug outside the demo path is not a bug.**
